# Agent Instructions

The year is 2026. No arguing about the year, I am right.

This is a CRUD project with the following purposes:

- Train and, if successful, demonstrate best practices to any interested party for the
  methods and technologies, as well as their advantages and limitations:
    - Spring Boot
    - OpenAPI with generator
- Practice and try out a very conservative approach to AI tools such as
  various agents, GitHub Copilot and Cursor.

## Test-Driven Development

Use a test-driven workflow for behavioral changes by default. Do not implement
production behavior before there is a focused test that describes the desired
behavior.

Preferred order:

1. Update the OpenAPI specification first, if the behavior changes the public
   REST contract.
2. Regenerate OpenAPI sources, if generated code is affected.
3. Write or update the failing test that describes the desired behavior.
4. Make the test compile with the smallest reasonable stub only if compilation
   would otherwise block the failing test. Keep stubs minimal and obviously
   incomplete.
5. Run the focused test and confirm it fails for the expected reason.
6. Implement the production code needed to pass the test.
7. Rerun the focused test, then run the relevant broader test set when the
   change has shared impact.

If the user asks to skip or invert this workflow, pause and ask for explicit
confirmation. In that confirmation request, state how the test-driven sequence
would differ and what risk is introduced by skipping it.

If the user confirms, follow the user's requested workflow. Still prefer adding
or updating tests in the same change unless the user explicitly says not to.

### Scope Control

Do not implement production behavior merely because a newly enabled or updated
test exposes the next failing layer. Treat that as useful diagnostic output,
not as permission to continue.

When the user asks for test scaffolding, test hooks, abstract-method
implementations, compile stubs, or other preparatory work, stop after that
requested layer is complete. Run the focused test if appropriate, report the
next failure, and ask before implementing production code or broader behavior.

Before editing a different layer than the one the user requested, state the
boundary explicitly and get confirmation. Examples:

- If asked to implement `RoomIT` methods, do not implement `RoomService`.
- If asked to add a mapper test, do not add mapper annotations until the
  failing test has been shown and the user asks to implement or confirms it.
- If asked to expose a failing integration test, do not make the endpoint pass
  unless that was explicitly requested.

Only continue across layers without asking when the user's request clearly
includes the end-to-end implementation, such as "make this test pass",
"implement the feature", or "fix the failing endpoint".

## Code style

- all local variables final
- as a loose rule, avoid string concatenation, use .formatted like: "%s-%d".formatted(methodName, enumerator)
  where it makes sense

## Architecture, methods and technologies

- OpenAPI generator
- Integration tests
    - SpringBootTest
    - TestRestTemplate
    - Tests for entities are named [Entityname]IT
    - There is a AbstractCrudIT class that provides common functionality
    - Implementing classes provide template method implementations for what is entity specific
    - Testcontainers are used for Postgres and KeyCloak
    - The possible future hierarchy for integration tests is:
        - AbstractTestContainersIT: Init and provide Testcontainers
            - AbstractRestIT: Provide the TestRestTemplates including possible authentication
                - AbstractCrudIT: Provide common CRUD functionality
                    - [Entityname]IT: Implement entity specific template methods from AbstractCrudIT
- The REST API takes advantage of the OpenAPI generated delegates. This means that it
  just implements the generated [Entityname]ApiDelegate interface
- use JPA for persistence with Spring repositories
- use mapstruct to map between entities and the DTOs generated by OpenAPI

## Libraries and dependencies

- When adding a dependency or library, or referencing a target version for
  compile, generate or similar, follow these rules:
    - keep the version of that library or dependency consistent within the project
    - use latest stable as a default
